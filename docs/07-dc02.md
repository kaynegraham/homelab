# 07: DC02, second domain controller

[Back to README](../README.md) · Previous: [06](06-pve02-cluster.md)

> Status: in progress. Promoted, health checks and failover testing next.

## Goal

Add a second domain controller on separate hardware. If pve01 or DC01 goes down, logins and DNS for `lab.twilight` keep working from DC02.

DC01 lives on pve01 and DC02 lives on pve02. Active Directory handles its own redundancy, so the DCs don't need Proxmox HA. Two DCs on two hosts is the redundancy.

## ISOs

ISOs live on each node's own `local` storage, so pve02 couldn't see the ones uploaded to pve01. Cluster nodes already trust each other over SSH, so they can be copied across instead of downloaded again. From pve02:

```
scp root@10.10.99.2:/var/lib/vz/template/iso/26100*.iso root@10.10.99.2:/var/lib/vz/template/iso/virtio-win.iso /var/lib/vz/template/iso/
```

The direction matters. Run on pve02, this pulls from pve01. Run on pve01, the paths need swapping.

## Install

1. At "Where do you want to install Windows?", Load driver, then browse the VirtIO CD to `vioscsi\2k25\amd64` so the disk shows up.
2. After install, the network card showed as "Ethernet Controller" in Device Manager with no adapter in `ncpa.cpl`. Ran `virtio-win-guest-tools.exe` from the VirtIO CD for the network driver and QEMU agent.
3. Set the network in PowerShell:

```powershell
New-NetIPAddress -InterfaceAlias "Ethernet" -IPAddress 10.10.99.12 -PrefixLength 24 -DefaultGateway 10.10.99.1
Set-DnsClientServerAddress -InterfaceAlias "Ethernet" -ServerAddresses 10.10.99.11
Rename-Computer -NewName DC02 -Restart
```

4. Checked DC01 and the domain were reachable before joining:

```powershell
ping 10.10.99.11
nslookup lab.twilight
```

5. Set the time zone. The Settings page is locked once a server is domain joined, but PowerShell still works:

```powershell
Set-TimeZone -Id "W. Australia Standard Time"
```

The clock itself was already right. Windows keeps time in UTC and syncs it from the domain, so only the displayed zone was wrong.

## RDP

RDP is off by default on Server 2025, and the Windows firewall blocks ping, so the server looks dead from outside even when it's fine.

```powershell
Set-ItemProperty -Path 'HKLM:\System\CurrentControlSet\Control\Terminal Server' -Name fDenyTSConnections -Value 0
Enable-NetFirewallRule -DisplayGroup "Remote Desktop"
```

Tested the port from the Mac with `nc -zv 10.10.99.12 3389`. Connected with Windows App (the renamed Microsoft Remote Desktop).

## OU structure

The built in `Users` and `Computers` are containers, not OUs, and a Group Policy can't be linked to a container. Created a top level `Twilight` OU to hold everything instead.

```
lab.twilight
├── Domain Controllers   (built in, DCs stay here)
└── Twilight
    ├── Servers
    ├── Computers
    ├── Users
    ├── Admins
    ├── Groups
    └── Service Accounts
```

- DCs stay in the built in `Domain Controllers` OU. Promotion moves them there automatically.
- Built in accounts like Administrator and krbtgt stay where they are.
- Day to day admin uses a named account in Domain Admins instead of the built in Administrator.

New objects can be pointed at the OUs so they don't land in the default containers:

```powershell
redircmp "OU=Computers,OU=Twilight,DC=lab,DC=twilight"
redirusr "OU=Users,OU=Twilight,DC=lab,DC=twilight"
```

## Domain join

```powershell
Add-Computer -DomainName lab.twilight -Credential TWILIGHT\Administrator -OUPath "OU=Servers,OU=Twilight,DC=lab,DC=twilight" -Restart
```

The first join ended up with a broken trust (see Issues hit), so DC02 was removed and joined again. Checked it with:

```powershell
Test-ComputerSecureChannel
```

`True` means DC02's computer account password matches what AD has. Took a snapshot before promoting.

## Promotion

DC01 has to stay running for the whole promotion.

```powershell
Install-WindowsFeature AD-Domain-Services -IncludeManagementTools
Install-ADDSDomainController -DomainName lab.twilight -InstallDns -Credential (Get-Credential TWILIGHT\Administrator)
```

It asks for a DSRM password (Directory Services Restore Mode, only used for recovery). Stored in the password manager.

## Issues hit

| Problem | Cause | Fix |
|---|---|---|
| pve02 had no ISOs | ISOs are on each node's local storage, not shared | Copied them across with `scp` |
| `scp` said no such file | Ran on pve02 with pve01's paths as the source | Swapped the direction to pull from pve01 |
| No disk in the installer | No VirtIO storage driver | Loaded `vioscsi` from the VirtIO CD |
| No network adapter | No VirtIO network driver | `virtio-win-guest-tools.exe` |
| Couldn't RDP or ping | RDP off by default, ping blocked by Windows firewall | Enabled RDP and its firewall rule |
| RDP from the Mac said the password had expired. Worked on DC01, failed on DC02. "Must change password" wasn't ticked. | Broken trust between DC02 and the domain: `Test-ComputerSecureChannel` returned `False` | Removed DC02 from the domain, deleted its computer object on DC01, joined again. `True` after. |
| Couldn't paste into the Proxmox console | noVNC doesn't pass the clipboard into Windows | Ran commands from DC01 with `Enter-PSSession -ComputerName DC02`, where paste works |
| `Test-ComputerSecureChannel -Repair` didn't fix it | Trust too far gone to repair in place | Rejoined instead |
| Wrong time zone, Settings locked | Domain joined servers lock that page | `Set-TimeZone` |

### Finding the real RDP error

Network Level Authentication (NLA) checks the password before the login screen appears, so the Mac only ever saw a vague "password expired" message. Turning NLA off for a minute showed the normal Windows login screen and the real behaviour:

```powershell
Set-ItemProperty 'HKLM:\System\CurrentControlSet\Control\Terminal Server\WinStations\RDP-Tcp' -Name UserAuthentication -Value 0
```

Set back to `1` once the trust was fixed. NLA stays on.

### Rejoining a server with a broken trust

```powershell
# On DC02, then log in as .\Administrator after the reboot
Remove-Computer -UnjoinDomainCredential TWILIGHT\Administrator -WorkgroupName WORKGROUP -Force -Restart

# On DC01
Remove-ADComputer DC02 -Confirm:$false

# On DC02
Add-Computer -DomainName lab.twilight -Credential TWILIGHT\Administrator -OUPath "OU=Servers,OU=Twilight,DC=lab,DC=twilight" -Restart
```

Most likely cause: a snapshot rollback or a rename and join that overlapped. Rolling a domain joined machine back to an older snapshot can leave it with an old computer account password that AD no longer accepts.

## Lessons

- Two DCs only count as redundancy if they're on different hardware.
- A false `Test-ComputerSecureChannel` causes strange login errors that don't mention trust at all. Check it before promoting anything.
- Don't promote a server with a broken trust. Fix the join first.
- PowerShell remoting from a working server gets around a console you can't paste into.
- NLA hides the real login error. Turning it off briefly is a quick way to see what's actually wrong.
- Snapshot before joining and before promoting, but never roll a DC back once there are two.
